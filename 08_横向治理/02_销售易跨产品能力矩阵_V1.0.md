# 销售易跨产品能力矩阵 V1.0

- 整理日期：2026-11-22
- 用途：售前方案架构、需求映射、产品选型、投标答疑
- 证据等级：A=最新正式产品手册/发布说明；B=官方公开资料；C=内部培训/产品介绍/客户版材料；D=历史方案/推断
- 当前矩阵主要基于B/C级资料，未取得正式功能清单的单元格不得作为合同承诺。

## 3. 典型场景架构原则

- 先识别业务主责产品，再确定协同产品；避免把所有产品能力都塞入单一模块。
- 数据整合不等于业务交易主系统；Data Cloud不应未经设计成为订单、合同或财务数据的权威源。
- NeoBI负责分析呈现，不自动承担源数据治理和跨系统同步。
- NeoAgent可通过工具参与业务流程，但其执行边界受权限、模型、工具、流程和确认机制限制。
- aPaaS用于应用扩展，集成平台用于系统间连接和数据/流程交互；重叠能力需以产品正式架构为准。
- 行业方案组合能力必须单独标记，不得写成某个单一产品开箱即用。

## 4. 证据缺口与高风险项

1. 各业务云最新正式产品功能清单、模块SKU和版本矩阵。
2. 伙伴云订货、返利、促销、伙伴门户能力的当前标准范围。
3. 服务云客户服务与现场服务的正式产品拆分和License。
4. NeoAgent当前Agent/Skill目录、租户范围、工具调用权限和执行确认策略。
5. aPaaS与Neo-Platform正式命名、产品边界和商业授权。
6. NeoBI数据源、刷新机制、数据量、指标建模和ChatBI可用范围。
7. Data Cloud与CDP正式命名、OneID实现、数据源/存储/计算/治理能力。
8. 集成平台连接器兼容清单、API配额、性能与SLA。
9. 各产品的部署选项、海外区域、数据驻留和安全认证范围。

## 5. 方案与投标使用规则

每项需求在方案中至少标注：
- 对应业务场景；
- 主责产品及协同产品；
- 能力类型（原生/配置/低代码扩展/定制/第三方集成/方案组合）；
- 依赖条件与数据来源；
- License/版本核验状态；
- 交付责任和验收标准；
- 证据来源及核验日期。
